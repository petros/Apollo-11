The code that flew
to the Moon and back

This repository holds the flight software for the two guidance computers on Apollo 11. One rode in the Command Module and one in the Lunar Module. This page is a map of what that code does and when in the mission it did it.

What is in the repository

Two folders, each a complete program written in AGC assembly language. The files are transcriptions of printed listings kept at the MIT Museum, typed up by volunteers from scanned pages. Each MAIN.agc lists its files in the order of the original printout, with page numbers.

Build 055 of Colossus 2A. It ran in the cone-shaped capsule that carried all three astronauts to lunar orbit and brought them home. Michael Collins flew with it alone while the other two were on the surface.

A large part of each program is the same in both, and many file names match. The two share an operating system, a math library, the keyboard and display code, and the orbital navigation routines. They differ where the vehicles differ.

The computer it ran on

Both spacecraft carried the same machine, the Block II Apollo Guidance Computer, designed at the MIT Instrumentation Laboratory. The figures below are the commonly published ones.

PropertyValue
Word size15 bits plus a parity bit
Program memory36,864 words of core rope, read only. The program was physically woven into it with wire.
Working memory2,048 words of magnetic core
WeightAbout 70 lb (32 kg)
PowerAbout 55 W
Crew interfaceThe DSKY, a numeric keypad and a few rows of digits

Memory, to scale

fixed (rope) 36,864 words

The thin strip on the left is all the RAM, 2,048 words. That is under 4 KB by today's counting, and the program is roughly 70 KB.

Why that shapes the code

The address field of an instruction could not reach all of memory, so the code is split into "banks" and has to switch between them. That is why you see BANK, SETLOC, BANKCALL and EBANK= everywhere. With so little RAM, many variables share the same cell at different times, which is what the long ERASABLE_ASSIGNMENTS file keeps track of.

Talking to it: the DSKY

The crew gave commands as a two-digit verb and a two-digit noun. The verb is the action and the noun is the thing acted on. Verb 16 Noun 36 means "keep showing me the clock". The code that runs all this is in a file the programmers named PINBALL_GAME_BUTTONS_AND_LIGHTS.

The 1202 alarm

A few minutes into the descent the lander's display showed alarm 1202, and it came back several times. The source says exactly what that code means. The Executive keeps a small table of running jobs, eight "core sets" in Luminary. When a new job is requested and every core set is taken, it gives up and restarts.

# Luminary099/EXECUTIVE.agc, lines 201-208
NEXTCORE	CAF	COREINC
		ADS	LOCCTR
		CCS	EXECTEM2
		TCF	NOVAC3
		LXCH	EXECTEM1
		CA	Q
		TC	BAILOUT1	# NO CORE SETS AVAILABLE.
		OCT	1202

The usual account of the cause is that a radar switch setting flooded the computer with useless interrupts, which took time away from real work. Jobs that should have finished were still holding core sets when their replacements arrived.

The restart did not lose the landing. The software records where each important job has got to (see PHASE_TABLE_MAINTENANCE and RESTART_TABLES), so after a restart it drops the backlog and picks the important work up again. Mission Control called "go" and the landing continued.

Reading the code

Every file has two kinds of code in it. Basic instructions run directly on the hardware. Interpretive instructions are a second, higher-level language for vector and matrix math, run by a small virtual machine in INTERPRETER.agc. It is slower but far more compact, which mattered in 36K of memory.

Layout of a line

LABEL		OPCODE	OPERAND		# COMMENT

# basic: is the landing radar antenna in position?
P63SPOT3	CA	BIT6
		EXTEND
		RAND	CHAN33
		EXTEND
		BZF	P63SPOT4

# interpretive: point the engine for the burn
P63SPOT2	VLOAD	UNIT

Both fragments are from THE_LUNAR_LANDING.agc.

You seeIt means
CA, CAFLoad a value into the accumulator, register A
TSStore A into memory
AD, ADSAdd
TC, TCFJump. TC remembers where to return, so it is also the subroutine call
CCSCount down and branch four ways on the sign. The usual loop instruction
EXTENDThe next instruction is from the second opcode set
INHINT, RELINTTurn interrupts off and back on
BANKCALL + CADRCall a routine that lives in another memory bank
TC INTPRETSwitch to interpretive code from here on
VLOAD, DLOAD, DOT, UNITInterpretive. Load a vector or double, dot product, normalize
OCT, DEC, 2DECConstants, not instructions
